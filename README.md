# xiaolu-vision-assistant

多人对话 AI 助手，通过特征词「小噜」唤醒，在群聊/多人场景中提供智能应答。

---

### 计划实现

|---|---------|--------|
| 1 | 作为群聊成员，我可以在对话中说「小噜 + 问题」，助手自动识别并回复 | P0 |

## 运营成本控制

### 考虑到的技巧

| # | 技巧 | 原理 | 状态 |
|---|------|------|------|
| 1 | **ASR 特征词频率控制** | 在客户端/网关层通过 ASR 实时识别「小噜」特征词，仅在检测到特征词后的 N 秒窗口内放行请求到 LLM，其余时间直接丢弃——避免全量语音流灌入大模型造成无效调用 | ✅ 已采用 |
| 2 | **开源 ASR 替换** | 后续将云端 ASR（如讯飞/阿里云）替换为开源方案（如 Whisper / Paraformer），消除 ASR 环节的按量计费，仅在 LLM 推理环节产生成本 | 📋 计划中 |
| 3 | **模型分级路由** | 简单问题（天气、时间、闲聊）路由到低成本小模型，复杂推理才用大模型 | 💡 备选 |
| 4 | **本地端侧推理** | 在设备端运行量化小模型处理高频简单查询，仅在本地无法满足时上云 | 💡 远期 |

### 成本链路示意

```
音频流 ──→ [ASR 特征词检测] ──→ 命中「小噜」──→ LLM 推理 ──→ 回复
               │                      │
               └── 未命中：静默丢弃    └── 频率窗口：N秒内只放行1次
```

- **ASR 环节**：当前使用云端 ASR，成本按音频时长计费；后续切换开源 ASR 后该环节成本趋近于零。
- **LLM 环节**：通过特征词 + 频率双重控制，确保只有真正意图提问的语音片段才会触发大模型调用，大幅减少无效 token 消耗。

## 技术栈（规划）

| 层 | 候选方案 |
|----|---------|
| ASR / 唤醒词 | 云端 ASR（短期）→ Whisper / Paraformer（中期） |
| LLM | 云端大模型 API |
| TTS | 云端 TTS 或端侧合成 |
| 消息通道 | 企业微信 / 飞书 / 钉钉 Bot API（按接入平台选择） |
